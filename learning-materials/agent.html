Agent（智能体）

一句话定义：Agent 是能够感知环境、自主决策并采取行动以达成目标的系统——在 AI 领域，通常指以大语言模型为"大脑"、能规划任务并调用工具完成的程序。

1学习目标

学完本资料后，你应当能够：

  1. 解释 Agent 的核心构成要素（感知—决策—行动—目标），并用自己的话向他人说明"Agent 和普通程序/聊天机器人的区别"。
  2. 区分 Agent 与 Workflow（固定流程编排）、Agent 与 Chatbot（纯对话）的边界。
  3. 分析一个具体的 AI 系统是否算 Agent：判断它是否具备自主性、目标导向性和环境交互能力。
  4. 应用 ReAct 等"推理 + 行动"的基本范式，描述一个简单 Agent 解决任务的循环过程。
  5. 评估 Agent 方案的适用场景与风险（何时该用 Agent，何时用固定流程更稳妥）。

2概念解释

🟢 一句话版本

Agent 是一个"给了目标就能自己想办法干活"的程序。

🟡 直观版本

想象你雇了一位助理。你不会手把手教他每一步，而是告诉他："帮我订一张下周去上海的最便宜的机票。"这位助理会自己拆解任务（查日期 → 比价格 → 选航班 → 下单），过程中使用工具（打开订票网站、调用支付），遇到问题会调整方案（那天的直达票太贵，就考虑中转），最后汇报结果。

Agent 就是这样的数字助理：普通程序像一台自动售货机（按固定按钮出固定饮料），而 Agent 像一位有判断力的员工——你给目标，它自己决定怎么做。

💡 关键直觉 判断是不是 Agent，问一个问题："它做事的路径是谁定的？" 路径写死在代码里 → 普通程序；路径由它自己临时规划 → 更接近 Agent。

🔵 严谨版本

在学术定义中（Russell & Norvig《人工智能：现代方法》），Agent 是通过传感器感知环境、通过执行器作用于环境的任何实体，其行为可用"感知序列到行动的映射"（策略 π）描述。形式化地，Agent = 感知（Perceive）+ 决策（Decide）+ 行动（Act），在环境 E 中追求目标 G 或最大化效用函数 U。

当代 AI 工程语境下的 LLM-based Agent 通常包含四个模块：

  • 规划（Planning）：将目标分解为子任务，常用的范式如 ReAct（Reason + Act，推理与行动交替进行）、思维链（CoT）、任务反思与重试（Reflexion）。
  • 记忆（Memory）：短期记忆（对话上下文）与长期记忆（向量库检索、文件持久化）。
  • 工具使用（Tool Use）：通过函数调用（Function Calling）操作搜索、代码执行、数据库、API 等外部能力。
  • 环境交互（Environment）：Agent 所作用的对象，如操作系统、互联网、软件界面。

与相邻概念的边界：

  • vs. Chatbot（聊天机器人）：Chatbot 以对话本身为产出；Agent 以"任务的完成"为产出，对话只是手段。
  • vs. Workflow（工作流）：Workflow 的步骤和分支由开发者预先编排，确定性高；Agent 的步骤由模型在运行时自主决定，灵活但可控性低。实践中常组合使用（Workflow 中嵌 Agent 节点）。
  • vs. Multi-Agent System（多智能体系统）：多个 Agent 分工协作（如规划者 + 执行者 + 审查者），是 Agent 概念的扩展形态。
⚠️ 常见误解
  • "接了 API 就是 Agent。" —— 不对。关键在自主决策，而非调用了多少外部能力。一个只按固定规则调 API 的程序不是 Agent。
  • "Agent 一定更高级、更好。" —— 不对。自主性带来灵活性的同时引入不可预测性和调试成本，Anthropic 在其构建经验中明确指出：能用 Workflow 解决的，就别上 Agent。
  • "Agent = 机器人。" —— 物理机器人只是 Agent 的一种载体（实体 Agent）；大量 Agent 是纯软件形态。

📜 来龙去脉

"Agent" 概念源于 1950–60 年代的控制论与早期 AI（如维纳的反馈控制思想）。1995 年，Wooldridge 与 Jennings 的经典论文《Intelligent Agents: Theory and Practice》系统化了软件 Agent 研究。2022 年 ReAct 论文与 2023 年 AutoGPT 的爆火，使"LLM + 工具 + 循环"成为当代 Agent 的主流形态；2025 年前后，MCP（Model Context Protocol）等协议进一步标准化了 Agent 与外部工具的连接方式。

3案例

日常案例 · 难度 ★

情境：你对手机助手说"提醒我明天出门带伞"。

概念体现：助手感知到请求（输入），查询明天的天气（调用工具），发现降雨概率 70%，于是创建了一条"明早出门前提醒"（行动），服务于"不被淋湿"的隐含目标。感知 → 决策 → 行动 → 目标，四要素齐备——这是一个（轻量的）Agent 行为。

结论：即使很小的任务，只要决策路径是系统根据目标自主选定的，就体现了 Agent 性质。

行业案例 · 难度 ★★★

情境：一个编程 Agent（如 Claude Code、Cursor Agent）收到任务："修复这个仓库里登录接口的 bug。"

概念体现：它自主规划步骤：读取报错日志 → 用 grep 搜索相关代码 → 阅读函数实现 → 定位空指针问题 → 修改代码 → 运行测试 → 测试失败 → 反思原因再修改 → 测试通过 → 提交。整个过程没有人事先写死步骤，路径是模型在循环中逐步生成的（典型 ReAct 模式），并且利用了反思重试这一 Agent 特有的纠错机制。

结论：编程是 Agent 落地最成功的领域之一，因为环境（代码库 + 测试）反馈明确，成功与否可以被客观验证。

进阶案例 · 难度 ★★★★

情境：客服系统中，商家希望"自动处理退款申请"。

概念体现：设计者采用 Multi-Agent 架构：一个"分类 Agent"判断申请类型与金额，一个"核查 Agent"查询订单与物流记录，金额小于阈值的直接由"执行 Agent"退款，大额或可疑的转人工。多个 Agent 各司其职、互相传递结果，共同完成一个复杂业务目标。

结论：当任务复杂到单一角色难以覆盖时，把 Agent 按职能拆分（规划者/执行者/审查者）是常见工程模式，本质是对人类团队分工的模拟。

反例 · 什么不是 Agent

情境：一个"智能客服"，用户点按钮进入"退款"分支，程序按 if-else 弹出固定话术，最后生成一张工单。全程没有任何模型自主决策。

辨析：它有输入、有输出、甚至有"流程"，但每一步路径都是开发者预定义的——它是 Workflow（或决策树），不是 Agent。它再"智能"，也只是自动化，不是自主化。

结论：判断标准不在交互形态像不像人，而在决策权在谁手里。

第 1 题（单选）Agent 区别于普通程序的最核心特征是？

答案：B

A. 能联网调用 API  B. 运行时自主决定行动路径  C. 界面用自然语言交互  D. 运行速度更快

解析：调用 API、自然语言交互都只是表象，固定 if-else 也能做到；核心区别是"决策权"从开发者转移到了系统本身（对应解释部分的"关键直觉"）。

考察学习目标 1、2
第 2 题（单选）"LLM + 工具调用 + 循环（观察结果后再决定下一步）"描述的经典范式是？

答案：C

A. Transformer  B. RAG  C. ReAct  D. GAN

解析：ReAct = Reason + Act，推理与行动交替，是当代 LLM Agent 的基础范式。RAG 是检索增强生成，属于"记忆"模块的一种实现。

考察学习目标 4
第 3 题（判断）只要一个系统使用了大语言模型，它就是 Agent。

答案：错误

解析：纯对话的 Chatbot 也使用 LLM，但它以对话为产出、无目标驱动的自主行动。LLM 只是 Agent 常用的"大脑"组件，不构成充分条件。

考察学习目标 2
第 4 题（判断）Workflow 的确定性比 Agent 高，所以在所有场景下都应该优先用 Workflow。

答案：错误

解析：前半句正确，但结论过度。面对步骤无法预先穷举的开放性任务（如"修复一个未知 bug"），Workflow 无法胜任，必须交给 Agent 在运行时自主探索。正确原则是"能 Workflow 则 Workflow，必须自主时才 Agent"。

考察学习目标 5
第 5 题（简答）说出 LLM-based Agent 的四个核心模块，并各举一个实现方式。

参考答案：① 规划（如 ReAct 循环、任务分解）；② 记忆（如对话上下文作短期记忆、向量数据库作长期记忆）；③ 工具使用（如 Function Calling 调用搜索/代码执行）；④ 环境交互（如操作系统、浏览器、软件 API）。

考察学习目标 1
第 6 题（简答）为什么说"编程"是 Agent 最容易成功的落地领域之一？

参考答案：因为编程环境的反馈客观且即时：代码要么编译通过要么报错，测试要么通过要么失败，Agent 的每一步行动都能得到明确信号来修正路线（可验证性强），大幅降低了自主决策跑偏的风险。相反，在反馈模糊的领域（如开放式写作），Agent 的自主性更难自我纠错。

考察学习目标 3、5
第 7 题（应用题）判断以下场景是否适合用 Agent，说明理由：每晚 22 点自动把当天的销售数据汇总成报表发到邮箱。

参考答案：不适合，用 Workflow/定时脚本更合适。理由：该任务目标明确、步骤固定、无运行时不确定性（取数 → 统计 → 渲染 → 发送），用确定性的自动化管道即可完成，更可靠、更便宜、更易调试。引入 Agent 只会增加不可预测性和成本。若需求改为"分析今天的销售异常并自主决定如何跟进"，才需要 Agent 的判断力。
