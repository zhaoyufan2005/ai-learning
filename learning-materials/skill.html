Skill（技能包）

一句话定义：Skill 是一份打包好的"操作说明书"，让 AI 助手在特定任务上按既定流程、用对工具、产出规范结果——相当于给 AI 发一本《标准作业手册（SOP）》。

学习目标 概念解释 案例 自测题 参考来源

1学习目标

学完本资料后，你应当能够：

  1. 解释 Skill 的本质（结构化提示 + 参考资源 + 工作流程），说明它与随手写的 prompt 的区别。
  2. 拆解 一个典型 Skill 的组成部分：元信息（frontmatter）、触发条件、指令正文、捆绑资源。
  3. 区分 Skill、System Prompt、Tool/MCP、微调四种"扩展 AI 能力"的手段及各自适用边界。
  4. 设计 一个简单 Skill：明确触发词、把隐性经验写成显性步骤、设置约束防止跑偏。
  5. 评估 什么时候值得把一段常用 prompt 沉淀为 Skill，以及 Skill 失效的典型原因。

2概念解释

🟢 一句话版本

Skill 就是"AI 的岗位技能卡"：遇到某类任务时自动掏出来照着做，做完的效果像一位受过培训的老手。

🟡 直观版本

新员工入职第一天，什么都要现学；而老员工的抽屉里放着一摞操作手册——"处理客诉看这本、报销走那张流程卡、周报用这个模板"。新员工每次都靠临场发挥（质量不稳定），老员工按手册办事（又快又规范）。

Skill 就是塞进 AI "抽屉"里的手册。区别在于：启用时机由 AI 自己判断——你说"帮我写周报"，它认出这匹配"周报技能卡"的触发条件，就把手册翻出来照着执行。你不用每次重新教，它也不会因为今天状态不同就换一套做法。

💡 关键直觉 Prompt 是一次性的口头交代，Skill 是沉淀下来的书面 SOP。判断标准：这段经验值得复用吗？要复用，就沉淀成 Skill；一次性任务，直接 prompt 即可。

🔵 严谨版本

在当代 AI 工程语境（以 Anthropic 于 2024 年 10 月发布的 Agent Skills 为代表）中，一个 Skill 是一个文件夹，核心是 SKILL.md 文件，通常还捆绑脚本与参考资源：

  • 元信息（YAML frontmatter）：名称、描述（description）、版本等。其中描述最关键——模型只靠读它来判断"当前任务要不要加载这个 Skill"，写得太笼统就会漏触发或误触发。
  • 指令正文：Markdown 写成的工作流程——步骤、规范、约束、易错点。这是 Skill 的"灵魂"，本质是结构化的提示词。
  • 捆绑资源（可选）：可执行的脚本（scripts/）、参考文档（references/）、模板文件（assets/）等，随指令按需使用。

运行机制：Skill 采用渐进式披露（Progressive Disclosure）——平时只有"名字 + 描述"常驻模型的上下文（占用极小），任务匹配时才把 SKILL.md 全文载入，需要时再读取捆绑资源。这解决了"经验多了塞不下上下文"的问题：不是全背下来，而是用到了才翻手册。

用户请求 ──► 模型扫描各 Skill 的描述（仅几百 token 常驻） │ ├─ 不匹配 ──► 正常回答（不加载任何 Skill） │ └─ 匹配 ──► 载入 SKILL.md 全文 ──► 按流程执行 │ └─ 需要时 ──► 读取捆绑的脚本/模板/参考文档

与相邻概念的边界：

  • vs. System Prompt（系统提示词）：System Prompt 是"人格底座"，每次都全量在场；Skill 是"专项手册"，按需加载。System Prompt 塞太多规则会挤占上下文且互相稀释——这正是 Skill 要解决的问题。
  • vs. Tool / MCP（工具）：Tool 给模型新的手脚（能调 API、能读数据库）；Skill 给模型新的章法（知道什么场景该做什么、怎么做才对）。二者互补：Skill 里常写明"何时调用哪个 Tool"。
  • vs. Fine-tuning（微调）：微调把能力烧进参数，改不动、成本高、但推理时不占上下文；Skill 是纯文本，随时可编辑、可版本管理（甚至放进 Git），但每次执行都占上下文。经验频繁迭代 → Skill；能力需要内化到"条件反射" → 微调。
  • vs. Prompt 库/收藏夹：Prompt 库需要人想起来去复制粘贴；Skill 由模型自动判断要不要用——自动化触发是分水岭。
⚠️ 常见误解
  • "Skill 是给模型安装的新功能。" —— 不对。模型本身没变，Skill 只是在正确的时机注入正确的指令，让已有能力被规范地引导出来。
  • "描述写得越全面越好。" —— 恰恰相反。描述是"触发器"，应当精准概括什么任务该用它；详细流程放正文，避免常驻上下文的浪费。
  • "有了 Skill 就万无一失。" —— Skill 是软约束，模型仍可能跳步或跑偏；关键步骤的产出需要检查项（checklist）兜底。

📜 来龙去脉

"把提示词模块化复用"的实践早已有之（Prompt 模板、SOP 提示）。2024 年 10 月，Anthropic 发布 Agent Skills 规范，把这一实践标准化为"文件夹 + SKILL.md + 渐进式披露"的形式，Claude 4/4.5 及第三方 Agent 框架（含 WorkBuddy 等助手产品）相继采纳，形成可分享、可安装的 Skill 生态——Skill 从个人备忘升级为可流通的经验资产。本仓库 .workbuddy/skills/concept-learner/ 下的 SKILL.md 就是一个实例。

3案例

日常案例 · 难度 ★

情境：你每天都让 AI"把这段会议录音整理成纪要"，前几次效果不错，后来某天它突然换了格式，还漏掉了待办事项。

概念体现：每次现写 prompt = 每次口头交代，质量随当天发挥波动。把要求沉淀为"会议纪要 Skill"（固定结构：决议/待办/责任人 + 触发词"整理纪要"）后，每次执行都走同一套章法，输出稳定可预期。

结论：Skill 的第一价值是一致性——把"偶发的好表现"变成"每次的默认表现"。

行业案例 · 难度 ★★★

情境：数据分析师的 AI 助手要处理"各类数据文件"：Excel 用一套流程（读表头 → 判断类型 → 公式校验），CSV 又是一套，遇到 PDF 附录还要先抽取表格。

概念体现：这些差异化的操作知识被写成若干个 Skill（表格处理 Skill、数据清洗 Skill），各自携带捆绑的校验脚本。模型接到"清洗这个 CSV"时自动匹配对应 Skill 并调用其脚本——领域经验以 Skill 形式在团队内分发，新成员的助手装上即用，无需口口相传。

结论：Skill 让组织里的隐性经验显性化、资产化，是团队知识管理的 AI 版落地。

进阶案例 · 难度 ★★★★

情境：本仓库正在使用的 concept-learner Skill：触发词是"学习/生成某概念的学习资料"。

概念体现：它体现了 Skill 设计的多个要点——① 元信息里写清触发条件（"当用户说'帮我学习 X'……"）；② 正文把"好学习资料长什么样"的隐性标准写成了显性规范（五段结构、三层解释、答案折叠、禁止编造链接）；③ 指定了输出位置和命名规则（learning-materials/<slug>.html），使每次产出可预测；④ 附自检步骤，防止模型偷工减料。

结论：写好一个 Skill 的核心功力，是把你"心里知道但没说出口"的质量标准全部写出来——模型不会读心，只会读字。

反例 · 什么不该做成 Skill

情境：某人把"翻译这段话成英文"也做成了 Skill，正文只有一句"请翻译成英文"。

辨析：该任务模型本来就会做，指令无增量经验、无流程、无规范——这是把 prompt 包装成 Skill 的过度工程。它不仅没收益，还多占常驻上下文、增加误触发面。Skill 的判断标准是"有没有值得复用的经验"，而不是"是不是一个 prompt"。

结论：一次性任务用 prompt，重复出现的专业流程才值得沉淀为 Skill。

第 1 题（单选）Skill 与普通 prompt 最核心的区别是？

答案：C

A. Skill 用了更高级的模型  B. Skill 一定包含可执行脚本  C. Skill 是可复用、可自动触发匹配的沉淀经验  D. Skill 不能修改

解析：Skill 本质仍是文本指令（不一定带脚本），但它被持久化保存、由模型根据描述自动判断启用，且随时可编辑。复用 + 自动匹配是它与"口头交代式 prompt"的分水岭。

考察学习目标 1、3
第 2 题（单选）在 Skill 的 YAML frontmatter 中，决定"模型会不会用上这个 Skill"的最关键字段是？

答案：B

A. name  B. description  C. version  D. 作者信息

解析：渐进式披露机制下，模型平时只能看到描述，凭它判断是否加载全文。描述写得含糊会导致漏触发（该用没用）或误触发（不该用却用了）。

考察学习目标 2
第 3 题（判断）Skill 会改变模型本身的参数，相当于一次轻量微调。

答案：错误

解析：Skill 是纯文本注入，运行时占上下文，不触碰模型参数；微调则通过训练永久改写参数。两者一个"外挂手册"、一个"内化肌肉记忆"，机制完全不同。

考察学习目标 3
第 4 题（判断）"渐进式披露"的意思是：所有 Skill 的全文始终驻留在上下文中，确保随时可用。

答案：错误

解析：恰好相反。平时只有"名称 + 描述"以极小代价常驻；正文在任务匹配时才加载，捆绑资源按需读取。若全部常驻，几十个 Skill 就会把上下文窗口挤爆。

考察学习目标 2
第 5 题（简答）说明 Tool/MCP 与 Skill 各自扩展了模型的什么，并举例说明二者如何配合。

参考答案：Tool/MCP 给模型新的能力（手脚）——如调搜索引擎、读数据库、发邮件；Skill 给模型新的章法（打法）——何时、何地、按什么规范去用这些能力。配合示例：一张"发票报销 Skill"写明流程"先用 OCR 工具提取票据 → 校验金额字段 → 调邮件工具发送给财务"，工具负责执行，Skill 负责编排与规范。

考察学习目标 3
第 6 题（应用题）团队里每周都有人问 AI "帮我把这份 PPT 大纲改好看点"，效果时好时坏。请判断：是否该沉淀为 Skill？若该，写出 SKILL.md 的关键内容框架。

参考答案：应该。判断依据：高频重复 + 存在"改得好"的隐性标准 + 现有表现不稳定。框架：① frontmatter：name 为 ppt-outline-polish，description 写清"当用户要求优化/美化 PPT 大纲时使用"；② 正文：输出规范（每页一句核心论点 + 最多三条支撑 + 演讲备注）、结构要求（总分总、每节页数限制）、风格约束（禁用空洞形容词、术语需统一）、易错点（不要擅自增加页数）；③ 自检清单（页数是否符合、每页是否有核心句）。

考察学习目标 4（设计）
第 7 题（应用题）某 Skill 上线后经常"该触发时不触发"。列出至少三个可能原因及对应修改。

参考答案：① description 太笼统（如"处理文档相关任务"）→ 改为包含具体触发动词和场景："当用户要求转换 PDF 为 Markdown / 提取文档结构时使用"；② 触发词汇与用户说法不匹配（Skill 写"整理纪要"，用户说"总结开会内容"）→ 在描述中列举同义说法；③ 与其他 Skill 描述重叠，模型选了另一个 → 划清边界，各自描述中写明"本 Skill 负责 X，Y 场景请用另一个"；④ 描述过短缺少上下文线索 → 补充典型任务示例。共同思路：把描述当作给模型的路由信号来优化。
